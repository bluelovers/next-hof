# 互動資料流設計最佳實踐（事前預防篇）

## 概述

回答「一個即時互動元件（拖曳 (drag)、縮放 (zoom)、旋轉 (rotate)、動畫 (animation)、即時讀值 (live readout)），從第一行程式碼起就該以什麼概念設計」，
讓那類除錯過程（量測、讀框架管線、拆防護後門）**根本不會發生**。

每一條原則都標註它消除了哪一段除錯。

---

## 一、核心觀念：頻率分層的資料通道

設計任何互動功能時，**第一個問題不是「資料存哪」，而是「這筆資料以什麼頻率流動」**。
三種頻率 = 三條彼此隔離的通道，永遠不混用：

| 通道 | 頻率 | 載體 | 規則 |
|------|------|------|------|
| **A. 即時通道** | 每幀（60fps） | 元件內部 `state` + `ref` 鏡像 | **絕不離開元件邊界**；不寫 store、不寫 props、不發事件 |
| **B. 讀值通道** | ~10Hz | 輕量模組級 pub/sub store | 單向：元件 publish → 讀值端 subscribe；**零 React 重繪**（ref 直更 DOM） |
| **C. 快照通道** | 手勢結束（1 次） | 宣告式管線（props／args／URL） | 只在 pointerup 等**收尾時**寫一次最終值；中途值一律不進 |

```
拖曳中：  pointermove ── rAF合併 ──▶ [A] 內部狀態 ── 每幀變動 ──▶ [B] live store ──~ 10Hz ──▶ 面板 DOM 直更
放開時：  pointerup ──────────────▶ [A] 最終值 ── 單次 ──▶ [C] args/props（宣告式快照，慢管線可接受）
```

**設計時的決策句（三問）**：

1. 「這筆資料每一幀都需要嗎？」→ **A**：留在元件內。
2. 「讀值端需要即時看到嗎？」→ **B**：publish 到 live store，讀值端直更 DOM。
3. 「只有收尾才需要嗎？」→ **C**：gesture 結束單次寫入。

> **消除的除錯**：卡頓（A 資料誤走 C 管線 → 每幀重繪整棵樹）、
> 放開後位移（C 管線的滯後中間值回流成回聲）——兩個症狀在設計階段即不存在。

## 二、六條設計原則

### 原則 1. 單一寫入點 + 值等冪 (Idempotent)

狀態的所有變更收斂到**一個函式**（如 `commitOffset`），它同時：

- 更新真相鏡像 ref（事件閉包／計時器永遠讀到最新值，不受 React 非同步提交影響）
- 更新 React state（**值相同直接 return**，避免無謂重繪）
- 發布到 B 通道（僅真的變動時）

```tsx
const commitOffset = (next: IOffset | null) =>
{
	const cur = offsetRef.current;
	const same = cur === next || (!!cur && !!next && cur.x === next.x && cur.y === next.y);
	offsetRef.current = next;
	if (same)
	{
		return;                     // 等冪：重複提交零成本
	}
	onLiveOffsetChangeRef.current?.(next);   // 通道 B
	setOffset(next);                         // 通道 A
};
```

外部同步也必須等冪：props 進來的值與內部相同 → no-op。
這樣**任何回聲天然無害**——用「值比對」取代「時間視窗」。

### 原則 2. 重管線隔離

框架的**序列化／非同步管線**（Storybook args、跨層 context 更新、postMessage、網路請求）
本質上「延遲且會合併」。設計規則：

- 重管線**不得出現在每幀路徑上**（它是通道 C 專用）。
- 讀取重管線的值時，**假設它可能是舊的**——用 ref 保存最新快照：

```tsx
const latestArgsRef = useRef(args);
latestArgsRef.current = args;               // 每次 render 都刷新
onClick={() => updateArgs({ ...latestArgsRef.current.pair, [side]: v })}   // 以最新值為底合併
```

> **消除的除錯**：跨框回歸（閉包抓舊 args 把另一側覆寫成舊值）、
> 讀框架原始碼（不再需要確認「管線到底多慢」——反正不用它）。

### 原則 3. 讀值零重繪 / Zero-re-render readouts

面板／徽章類讀值**不是 React 狀態的用途**。規則：

- 讀值 DOM 用 `ref` 直接寫 `textContent`（B 通道 listener 內），
  **不可**用 `useState` 觸發面板重渲染、更不可連帶重繪整棵樹。
- 需要 React 化的讀值（列表、樣式化）用 `useSyncExternalStore` 訂閱 B 通道，
  store 快照引用必須穩定（值變動才換物件）。

> **消除的除錯**：rAF 幀距尖峰歸因——重繪源頭消失，無需再歸因。

### 原則 4. 收尾單次提交

手勢（拖曳、旋轉、縮放）的**資料語意**是「結果」而非「過程」：
過程屬於視覺（A），結果屬於宣告（C）。因此：

- pointerup／pointercancel：把 A 的最終值**寫一次** C。
- 僅在「與外部現值不同」時寫（拖回原位、純點擊 → 零寫入、零重繪）。
- 拖曳過程中的 C 寫入數量恆為 **0**——這是可斷言的設計不變式：

```tsx
// 設計不變式 / design invariant
// dragActive ⇒ writesToHeavyPipeline === 0
```

> **消除的除錯**：滯後堆積；「放開後位移筆數」指標恆為 0。

### 原則 5. 純函式抽離 / Pure-function extraction

對齊、吸附、收斂、座標／百分比格式化等**運算邏輯全部抽到無 React、無 DOM 的
utils 模組**（如 `editModeUtils.ts`），元件只做「接線」：

- 可用 fake timers／固定輸入寫單元測試（設計時就附上）。
- 元件內剩餘的除錯面積縮到「接線錯誤」一種。

> **消除的除錯**：運算類 bug 的實機反覆驗證——單測一次鎖定。

### 原則 6. 可觀測性內建 / Built-in observability

設計時就讓「未來的症狀」可量化：

- 編輯／預覽模式掛**座標徽章**（當前值一眼可見、可截圖對比）。
- 讀值 DOM 給測試腳本留穩定的選擇器（class 或文字前綴）。
- 合成測試友善：關鍵互動走標準 pointer events（可被合成派發重現）。

> **消除的除錯**：症狀量化從數小時縮到數分鐘——指標本來就在畫面上。

## 三、反模式清單

| 反模式 | 為什麼錯 | 正確做法 |
|--------|---------|---------|
| 每幀／每事件寫回 props 或 args | 重管線在即時迴圈內 → 卡頓＋回聲 | 通道 A 留元件內；C 只在收尾單次寫 |
| 用防護視窗／計時器處理回聲 | 視窗到期行為本身是後門（把舊值補寫回來） | 值等冪比對；或根本不產生回聲（單次寫入） |
| 面板讀值經由 React state | 拖曳期間整樹重繪 | ref 直更 DOM；或 useSyncExternalStore + 穩定快照 |
| 閉包直接抓 args／props 做合併 | 管線滯後 → 合併基底是舊值 → 跨物件回歸 | `latestRef.current` 每次 render 刷新 |
| 以 `Date.now()` 節流「視覺+回報」共用路徑 | 視覺被回報拖慢、回報又拖慢視覺 | 視覺每幀（rAF 合併）；回報不做（單次收尾） |
| 在元件內寫運算邏輯 | 無法單測、只能實機驗證 | 抽純函式 utils + 同步補測試 |
| rAF 直接傳多參函式 | rAF 傳入的時間戳被當成參數（如 force=true） | 傳無參函式或箭頭包一層 |
| 安全網補同步不審查到期值 | 到期時讀到的是滯後值 → 補同步等於製造 bug | 到期行為必須與正常路徑同值；否則移除計時器 |

## 四、設計時檢查清單

新功能動工前逐項確認：

- [ ] 這筆資料的**頻率**是 A／B／C 哪一通道？寫下來。
- [ ] 每幀路徑上沒有任何重管線呼叫（props 回報、args 寫入、store 重型通知）。
- [ ] 所有狀態變更經**單一 commit 函式**；ref 與 state 同步、值相同跳過。
- [ ] 外部同步（props → 內部）值等冪；**沒有**任何計時器型防護。
- [ ] 收尾寫入僅在「與外部不同時」執行；拖曳中寫入數恆為 0。
- [ ] 讀值端不經 React 重繪（ref 直更 DOM 或 useSyncExternalStore 穩定快照）。
- [ ] 合併外部快照用 `latestRef` 模式，不用閉包抓值。
- [ ] 運算邏輯已抽純函式，並附單元測試（含 fake timers 場景）。
- [ ] 畫面自帶可觀測性（座標徽章／穩定選擇器），症狀可被合成測試量化。
- [ ] 知道 `pnpm run test` 的 tsc 是非阻斷式——驗證要看 `grep "error TS"`。

---

> **總結**：開工前先畫「頻率分層的三條通道」——每幀資料留在元件內、
> 讀值走旁路、宣告快照只在收尾寫一次。除錯指南裡的每一步，
> 都是這三條線畫錯的痕跡。
