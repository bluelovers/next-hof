# 根因優先除錯指南 / Root-Cause Debugging Guide

## 概述

本指南沉淀自 `dual-frame-editable` 拖曳卡頓與放開後位移的修正案例。

核心教訓：**補丁會循環——症狀沒消失時，代表第一次的「根因」其實只是猜測。**
流程為「先量測、再讀管線、最後才動架構」，事前預防請見
`docs/interaction-dataflow-best-practices.md`。

---

## 一、基本原則

### P1. 症狀必須先能量測化

使用者的形容（「卡頓」「繼續移動」）無法驗證修正是否有效。
先把每個症狀轉成**可計數的指標**，之後每次修正都對同一組指標負責：

| 症狀 | 量化指標 |
|------|---------|
| 卡頓 | 拖曳期間 rAF 幀距 >50ms 的次數、最大幀距 |
| 放開後移動 | pointerup 之後 inline style 變化的筆數與時間偏移 |
| 讀值落後 | 座標讀值與實際位置的差、args 更新到畫面的延遲 |

### P2. 先驗證量測器本身有效

無效的量測環境會產出看似合理的假數據。**每次量測先跑 0.5 秒健康檢查：**

```js
// 背景節流的特徵訊號 / signatures of background throttling
// - rAF 在 500ms 內 0 次觸發（分頁被遮蔽或背景）
// - setInterval(16) 實際間隔被壓到 ~1000ms
// - longtask 陣列永遠為空（沒有活動可觀測）
({ rafTicksIn500ms: n, visibility: document.visibilityState, hasFocus: document.hasFocus() })
```

**`rafTicks` 為 0 或 timer 間距 ≈1000ms → 該輪量測作廢**，先將頁面前台化
（`page.bringToFront()`）再重測。別拿節流環境的數據下結論。

### P3. 機制解釋優先於相關性

「12 個卡幀、9 次 args 更新」只是**線索**，不是結論。
假說必須能解釋**全部**症狀，並對尚未觀察的面做出可驗證的預測：

- 為什麼關掉吸附卡頓仍在？（→ 卡頓源與吸附無關）
- 為什麼短拖曳沒問題、轉幾圈才有？（→ 與拖曳時長／堆積量成正比）
- 為什麼修正後仍發生？（→ 修正本身是否引入了新路徑）

### P4. 動態工具被擋時，讀框架原始碼

量測工具被限制（CDP 遭拒、無法重啟服務）不代表只能猜。
**被質疑的資料管線，每一站都寫在 `node_modules` 裡**：

```
frame.updateArgs → channel.emit → store.args.update（同步合併）
→ StoryRender.rerender() → render() → await waitForAnimations()
  → setTimeout(100) + getAnimations() 檢查   ← 每次 rerender 至少 +100ms 的管線地板
```

本案關鍵證據（管線地板 ≥100ms 對撞 10Hz 回報）**全部來自靜態閱讀**，
不需任何執行期工具；`grep`／`read` 永遠不會被擋。

### P5. 區分補釘與架構修正

當**框架的根本設計**與需求衝突時，繼續加防護只是把後門越挖越多：

| 特徵 | 補釘 | 架構修正 |
|------|------|---------|
| 做法 | 節流、防護視窗、重試、安全網 | 把該資料移出衝突的管線 |
| 症狀 | 修正後仍出現或換個形式出現 | 結構上不可能發生 |
| 新風險 | 防護本身過期／失效時反噬 | 無（路徑縮短） |
| 適用 | 管線本身正確、只是偶爾趕不上 | 管線根本不該在 60fps 迴圈裡 |

**決策句**：「這筆資料每一幀都需要嗎？」→ 放在迴圈內（state／ref）；
「只有收尾才需要嗎？」→ 只寫一次（pointerup）；
「讀值端需要即時嗎？」→ 輕量 pub/sub store 繞過重管線。

## 二、工作流程

```
Step 1 症狀量化 → Step 2 量測器健檢 → Step 3 動態證據 → Step 4 靜態讀管線
       → Step 5 機制假說（須解釋全部症狀）→ Step 6 補釘 vs 架構 → Step 7 驗證
```

### Step 1. 症狀量化

定義固定指標（見 P1），並寫一個**可重複執行的合成測試**
（例如頁內派發 PointerEvent 畫圓、rAF 取樣器記錄 inline style）。
每次修正後跑同一支腳本比對。

### Step 2. 量測器健檢

見 P2。另注意**儀器污染**：取樣器若每幀做昂貴操作
（`querySelectorAll`、大量 `textContent`），會把卡頓「測」出來。
取樣路徑必須只讀快取的 ref 與 inline style。

### Step 3. 動態證據

三件套同時掛上，讓時間軸可互相对齊：

1. **rAF 幀距取樣** — 每幀記錄 `{時間, 幀距, 位置}`（卡幀在哪一刻發生）
2. **longtask 觀測** — `PerformanceObserver({ entryTypes: ['longtask'] })`
3. **事件時間戳** — `MutationObserver` 盯讀值 DOM（args 更新到達時刻）、
   `pointerdown`／`pointerup` 記錄（分隔拖曳期與放開後）

**歸因手法**：把卡幀時間戳與事件時間戳做 ±250ms 配對，並比對**數量**是否吻合
（12 卡幀 vs 9 次更新 → 強烈暗示同源）。工具被擋時以頁內 observer 替代，效果等價。

### Step 4. 靜態讀管線

對每個「資料的生產者 → 消費者」路徑，列出**實際**（不是你以為的）步驟，
標註每步的同步／非同步、合併、延遲：

- 框內部狀態（rAF 每幀，同步）→ 快
- `updateArgs` → StoryRender（非同步、pending 合併、每次 ≥100ms）→ 慢管線
- 輕量 store 通知（同步 listener、無管線）→ 快

### Step 5. 機制假說

用一句話寫出完整因果鏈，**每個症狀都必須掛得上去**：

> 拖曳中 10Hz 回寫 args → 每次回寫重繪整棵 story 樹（卡頓）；
> 放開時 500ms 回聲防護 (echo guard) 到期，但管線尚未送達最終值 →
> 防護把**舊 args 值**補寫進框、並解除防護讓排隊中的舊值逐個套用（放開後繼續移動）。

反證自查：若假說為真，短拖曳（堆積小）應症狀輕、調整防護時長只會改變頻率
而無法根除——兩點都與觀察吻合。

### Step 6. 決定修正層次

依 P5 決策表。本案判定：**args 是序列化的慢管線，根本不該在 60fps 拖曳迴圈內**
→ 中間值完全不經過 args（live store 直通讀值端），只在 pointerup 寫一次；
隨之把節流／防護／安全網**整套拆除**（防護存在的理由——回聲——已消失）。

**修正是「刪掉機制」而非「加上機制」，是根因找對了的最強訊號。**

### Step 7. 驗證

1. **自動化**：新純函式／store 必須配單元測試（fake timers 驗證節流與尾端送達）。
2. **一次跑完**：`pnpm run test`（型別檢查 + 單元測試）。
   ⚠️ `test:tsc` 是**非阻斷式**（`&` 分隔）——必須確認 `grep "error TS"` 為 0 筆，
   不能只看 exit code。
3. **實機手感**：Storybook 對同一組指標重測（卡幀數、放開後位移筆數），最後才是主觀手感。
4. **確認修正真的生效**：確認開發伺服器吃到的是你改的程式碼（無 HMR 錯誤），
   避免拿舊 bundle 判定「沒修好」。

## 三、常見陷阱

| 陷阱 | 症狀 | 避免方法 |
|------|------|---------|
| 量測環境被節流 | rAF 停擺、數據全空或全怪 | 先跑健檢（P2），前台化後重測 |
| 儀器污染 | 量測本身造成卡幀 | 取樣只讀快取 ref／inline style |
| 只信相關性 | 修了巧合、症狀復發 | 機制假說須解釋全部症狀（P3） |
| 防護機制成後門 | 「修好」的東西反而製造症狀 | 審查每個安全網到期時的行為（本案 500ms 計時器） |
| 框架管線靠猜 | 反覆試錯不中 | 直接讀 `node_modules` 實作（P4） |
| 舊 bundle 判死 | 「完全沒解決」但程式碼已對 | 確認伺服器吃到新程式碼 |
| exit code 假陰性 | 型別錯誤通過 | `grep "error TS"` 必須為 0 |
| 補釘循環 | 一修再修 | 觸發 P5 重判：資料該不該在這條管線裡 |

## 四、案例對照

| 階段 | 本案實際內容 |
|------|-------------|
| 症狀 | 拖曳卡頓（>50ms 卡幀 ×12／1.3s）；放開後框繼續移動 |
| 第一版修正（猜測） | 10Hz 節流 + 回聲防護 → 用戶回報「完全沒解決」 |
| 動態證據 | rAF 幀距尖峰與 args 更新數量吻合（12 vs 9）；讀值落後 ~150ms |
| 量測陷阱 | Playwright 頁面背景節流（`rafTicks=0`）→ 該輪數據作廢 |
| 靜態證據 | `waitForAnimations` 每次 rerender `setTimeout(100)` → 管線地板 ≥100ms |
| 機制假說 | 10Hz 回寫對撞 ≥100ms 管線 → 重繪卡頓 + 積壓回聲；500ms 防護到期是後門 |
| 架構修正 | args 移出拖曳迴圈：live store 直通讀值、pointerup 單次寫回；拆毀全套防護 |
| 驗證 | store／格式化單元測試、`pnpm run test`（`error TS` = 0 筆）、Storybook 手感 |

---

> **一句話總結**：症狀先量化、量測先健檢、管線讀原始碼、假說須過反證；
> 當修正需要「防護」才能成立時，先問這筆資料為什麼會出現在這裡。
